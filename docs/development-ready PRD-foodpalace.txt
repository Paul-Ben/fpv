# FoodPalace — Product Requirements Document (PRD) & Software Requirements Specification (SRS)

**Project:** FoodPalace
**Product Type:** Multi-vendor food ordering, payment and delivery platform
**Target Market:** Nigeria initially, with architecture suitable for expansion
**Frontend:** Next.js + TypeScript
**Backend:** Laravel API
**Database:** PostgreSQL
**Database Hosting:** Supabase
**Backend Hosting:** Railway
**Frontend Hosting:** Vercel
**Payment:** Paystack and/or Flutterwave
**Architecture:** API-first, modular, multi-vendor platform

---

# 1. Executive Summary

**FoodPalace** is a multi-vendor food ordering and delivery platform that connects:

1. **Customers** who want to discover food vendors, browse menus, order food and make payments.
2. **Food Vendors** who want to register their food businesses, advertise their outlets, publish menus and receive/manage customer orders.
3. **Dispatch Riders/Delivery Personnel** who collect orders from vendors and deliver them to customers.
4. **Administrators** who manage the platform, vendors, customers, payments, orders, dispatch operations, commissions and platform configuration.

The system will provide an end-to-end workflow:

> **Customer → Browse Vendor → Select Food → Cart → Checkout → Payment → Vendor Confirmation → Food Preparation → Dispatch Assignment → Pickup → Delivery → Customer Confirmation → Order Completion**

FoodPalace should initially be designed as a **single-city/local-market platform**, but the architecture should support multiple cities, vendors, delivery zones and expansion later.

---

# 2. Product Vision

FoodPalace aims to become a reliable digital marketplace for discovering and ordering food from local restaurants, fast-food outlets, caterers and independent food vendors.

The platform should solve several common problems:

### Customers

* Difficulty discovering nearby food vendors.
* Lack of accurate online menus.
* Difficulty placing orders through phone/WhatsApp.
* Uncertainty about order status.
* Payment inconvenience.
* Difficulty tracking deliveries.
* Lack of reliable delivery confirmation.

### Vendors

* Limited digital visibility.
* Lack of an online ordering system.
* Difficulty maintaining digital menus.
* Manual order management.
* Difficulty managing delivery requests.
* Lack of customer/order analytics.

### Dispatch

* Unstructured delivery assignments.
* Difficulty knowing pickup and delivery locations.
* Lack of delivery confirmation.
* Poor visibility into completed deliveries.

### Platform

* Need for centralized vendor management.
* Commission management.
* Order/payment monitoring.
* Vendor verification.
* Delivery management.
* Reporting and analytics.

The system should initially support the following roles.

| Role                | Description                      |
| ------------------- | -------------------------------- |
| Super Administrator | Complete platform control        |
| Administrator       | Platform operations              |
| Vendor              | Food business owner/operator     |
| Vendor Staff        | Vendor employees managing orders |

| Dispatcher          | Handles food pickup and delivery |
| Dispatcher Manager  | Manages dispatch operations      |

# 21. Order Placement

When a customer clicks:

> **Place Order**

The backend should:

1. Validate cart.
2. Validate vendor status.
3. Validate menu availability.
4. Validate prices.
5. Calculate order total server-side.
6. Calculate delivery fee.
7. Create order.
8. Create order items.
9. Create payment record.
10. Initialize payment.
11. Return payment authorization information.

**The frontend must never be trusted to calculate the final payable amount.**

# 23. Payment Webhooks

Payment providers must communicate with Laravel through secure webhooks.

Example:

```text
Paystack
    ↓
Laravel Webhook
    ↓
Verify Signature
    ↓
Verify Transaction
    ↓
Update Payment
    ↓
Update Order
    ↓
Notify Customer/Vendor
```

Never mark an order as paid based solely on the frontend redirect.

The backend must verify the transaction independently.

# 45. Commission System

Example:


```text

₦10,000 - ₦1,000
```

* Fixed fee

# 81. Key Business Rules

### Rule 1

Only approved vendors can publish menus and receive orders.

### Rule 2

Only active menu items can be ordered.

### Rule 3

Prices are always calculated server-side.

### Rule 4

Only successful payments can move an order to the paid state.

### Rule 5

Payment confirmation must come from verified gateway communication.

### Rule 6

Only vendors can accept/reject their orders.

### Rule 7

Only assigned dispatchers can update their deliveries.

### Rule 8

Pickup must occur before delivery confirmation.

### Rule 9

Delivery OTP can only be used once.

### Rule 10

Only completed orders can generate reviews.

### Rule 11

Customers cannot modify an order after vendor preparation has started unless the business rules explicitly allow it.

### Rule 12

Every important order state transition must be recorded.

# 105. Critical Order Architecture

One of the most important parts of FoodPalace should be a formal **Order State Machine**.

Do not allow arbitrary status changes such as:

```text
Controller:
$order->status = 'delivered';
```

Instead:

```text
Order
 ↓
Transition
 ↓
Validate allowed transition
 ↓
Record history
 ↓
Fire event
 ↓
Notify users
```

For example:

```text
READY_FOR_PICKUP
       ↓
DISPATCH_ASSIGNED
       ↓
PICKED_UP
       ↓
OUT_FOR_DELIVERY
       ↓
DELIVERED
       ↓
CUSTOMER_CONFIRMED
       ↓
COMPLETED
```

This will make the application substantially more reliable.

## Final Product Architecture

The resulting FoodPalace platform should essentially be a **three-sided marketplace**:

```text
                    FOODPALACE
                         │
        ┌────────────────┼────────────────┐
        │                      │                      │
        ▼                      ▼                 ▼
   CUSTOMER           VENDOR          DISPATCHER
        │                │                │
        │                │                │
     Browse          Publish Menu       Receive Job
        │                │                │
     Order            Receive Order      Pickup
        │                │                │
     Payment          Prepare Food       Deliver
        │                │                │
        └────────────────┼────────────────┘
                         │
                         ▼
                       ADMIN
                         │
             ┌───────────┼────────────┐
             ▼           ▼            ▼
          Payments     Vendors      Operations
             │           │            │
             └───────────┼────────────┘
                         ▼
                     Analytics
```

The most important architectural decision is to treat **FoodPalace as an API-first multi-vendor marketplace**, rather than simply a restaurant website. Laravel should own **authentication, authorization, pricing, order state, payment verification, commissions, delivery state and business rules**, while Next.js should primarily own the presentation and user interaction layer.

For the first production version, I would also **avoid overbuilding live GPS tracking, automated dispatch optimization, multi-vendor carts, complex subscriptions and sophisticated advertising bidding**. Build the transaction engine first, validate the business model, and then layer those capabilities on top.
